# Save formats observed in the Steam builds

## Pocket City

The Steam package starts at `resources/app/cdv-electron-main.js`. The renderer loaded by `index.html` uses a localized `app_<locale>.js` bundle. The English bundle contains `ElectronFileStorage`, which requests Electron's `userData` directory through a preload bridge. The older Cordova `FileStorage` class is also shipped and uses different filenames.

- `_cities.save` maps local slot numbers to city identifiers.
- `_city_<ID>.save` stores one city's automatic (`AS`) and manual (`MS`) snapshots. Each snapshot has a timestamp, metadata, statistics and map grids. The game compares the timestamps at index zero of each list when choosing the latest snapshot.
- `_user.save` is the separate user settings file. The game writes sibling `.bk` files and can fall back to them when the primary file is invalid.
- The JSON snapshot text passes through the game's token substitutions, then a worker replaces runs of `"",` with `^count~`. Four substitutions also replace the colon after certain object keys. The editor parses those keys while retaining their original representation.
- City names are stored in `metadata.name` and the balance is stored in `stats.money`. An edit can target one snapshot without changing the others or the slot index.
- Level and experience are separate fields under `stats.level` and `stats.exp`. The next level costs `1500 + (level - 1) * 150` experience. Setting the level in a save updates the stored level directly.

REA evidence for the Electron entry point and the two workers is recorded under `ev_982e026d80d6b69f4f0b7cb167c4ef0c9b7e5bf11ef5ba1c27de1bd34906bab9`. Ghidra imported the Steam executable as a PE. The save-specific behavior was traced in the JavaScript bundle and checked against files generated by a disposable game profile.

## Pocket City 2

The Steam build is a Unity Mono game. The gameplay assembly is `Pocket City 2_Data/Managed/Assembly-CSharp.dll`, SHA-256 `2c2c55413241432ed6fe1aaa22d7f9879c4b174b55b38eecc997f6ab815e8fe6`. REA recorded the CLI metadata and the CIL members of `IO`, `GameState` and `SurvivalMode` under `ev_e58d27166ef096d5dcef971bcbb68e42d78d53a4ccd82f53db89005b1122e690`.

- City files wrap a `GameState` under `CITY.value`. Settings use `SETTINGS.value` or `OS.value`.
- `IO.TryLoadGzip` first attempts Easy Save 3 gzip and retries with the plain format. Six local city files and the available settings used gzip. The decoded text contains unquoted numeric keys and can contain trailing commas. The editor keeps the original document and replaces only the selected scalar spans.
- `city_<ID>.es3` is the primary save. `_auto_` and `_manual_` files live alongside it. The game looks for the primary file first, falls back to an automatic archive when missing and compares the result's filesystem timestamp with the latest manual archive.
- `GameState.money` is a signed 64-bit integer. Level, day, XP and most numeric dictionary values are 32-bit integers. Resource, relationship, vehicle, research and survival settings are separate fields.
- `Relationships.ResolveRelationship` maps NPCs to 16 independent profiles, including shared citizen, worker and small-business profiles. The game clamps the stored score to 0–999 and uses a base score of 1 for missing entries. A direct score edit does not run the gameplay routine that queues relationship gifts and unlock notifications.
- `GameController.AddXP` reads `GameState.level` and `GameState.XP` separately. The default threshold is `2000 + (level - 1) * 40`. Survival mode uses separate progression rules.
- `Buildings.isUnlocked` and `Buildings.isUnlockedByLevel` first check `GameStateHelper.isBuildingForceUnlocked`. A key under `forceUnlockedBuildings` passes this check independently of the stored level and sandbox. The game checks key presence, so writing `false` leaves the unlock active. Already present entries appear as checked and read-only. The editor's catalog derives IDs from `Tile.VALUE` and progression requirements from the installed `Buildings` metadata.

Ghidra imported the PE and identified CLI structures. Its default x86 analysis timed out on the CIL assembly. A focused read-only Ghidra script verified the CIL body hashes against REA evidence `ev_1edf907d586e91a6cd60f534271d55d688723a924adfeec6f39f01680811f2ad` for `GetRelationship` at `004bd060`, `AddXP` at `00517b80`, `ForceUnlockBuilding` at `005199cc`, and `isBuildingForceUnlocked` at `005199e4`. Focused ILSpy output and actual save files corroborated the format.
